# WebGen Control Service

A root-run, host-side internal HTTP service for the DCK WebGen lifecycle. It uses Python stdlib HTTP/subprocess/urllib, pinned `cryptography` for AES-GCM encryption, and pinned PyYAML to reject unsafe Compose features. It is reached through the authenticated parent Canvas proxy; it has no CORS support and binds only to the private Docker host gateway (`WEBGEN_BIND_HOST`, default `172.17.0.1`), never a public interface.

## Run and test

```sh
python3 -m venv .venv-webgen
.venv-webgen/bin/pip install -r services/webgen-control/requirements.txt
sudo .venv-webgen/bin/python -m unittest discover -s services/webgen-control/tests -v
```

Run these tests from the repository root on an isolated Linux test host with nginx installed. Production uses the systemd unit installed by `scripts/dck-deploy.sh`; see [deployment](DEPLOYMENT.md).

Environment: `WEBGEN_WORKSPACE_ROOT` (default `/opt/dck-agentic/workspace`), `WEBGEN_NGINX_DIR` (default `/etc/nginx/dck-apps`), `WEBGEN_CANVAS_AUTH_URL` (`http://127.0.0.1:8012/api/workspaces`), `WEBGEN_CONTROL_KEY` (default `/var/lib/dck-webgen-control/webgen-control.key`, created atomically mode 0600), `WEBGEN_CONTROL_STATE_DIR` (default `/var/lib/dck-webgen-control`), `WEBGEN_RUNTIME_DIR` (systemd uses `/run/dck-webgen-control`, a volatile root-only directory), `WEBGEN_BIND_HOST`, and `WEBGEN_CONTROL_PORT` (default `8769`). The deploy script discovers the bridge gateway rather than relying on the service default. `WEBGEN_POSTGRES_USER` comes from deployment `POSTGRES_USER`; database maintenance connects to `postgres`.

## Authentication and project scope

Every API request requires `X-Session-API-Key`, validated against the Agent Server through the read-only internal proxy on loopback 8012. The proxy forwards only workspace and secret GETs; it has no write route. Public Canvas ingress remains portal-cookie protected. Runtime-secret routes accept a project slug, resolve it to a canonical project directory, and use a unique stable UUID persisted as non-secret `.dck.json` metadata. Corrupt/unreadable metadata, duplicate IDs, and malformed IDs fail closed without rewriting the file. The encrypted store is indexed by that UUID—not by the slug—and each request is scoped to the resolved project. `/healthz` is intentionally unauthenticated and reveals only `{status:ok}`.

## Runtime secrets are separate from Agent Secret Manager

App Environment values and per-key Sensitive/Non-sensitive classifications are encrypted at rest in `/var/lib/dck-webgen-control/runtime-secrets.enc` with AES-GCM. The master key is `/var/lib/dck-webgen-control/webgen-control.key`; both the state directory and key/store files are root-only, and the key is never inside Canvas's `./config` bind mount. Deployment migrates an existing `config/webgen-control.key` only when its bytes match or the private copy does not yet exist; conflicting keys stop deployment for manual recovery. New and legacy values default to Sensitive. List/status responses expose names, configured state, classification, and migration metadata only. The separate value endpoint requires the existing authenticated session check, returns only the requested value, and uses `Cache-Control: no-store` plus `X-Content-Type-Options: nosniff`. Classification is descriptive: both categories stay encrypted and app-only, and neither is available to agents. Values are never written to prompts, transcripts, logs, analytics, Git, or build inputs and are not inserted into Agent Secret Manager or exposed through `LookupSecret`.

On an explicit deploy-like action, projects with `needsDatabase: true` or Better Auth receive a stable generated `DATABASE_URL` if none is already configured. The host provisions a per-project database, a non-owner app runtime role, and a separate database-owner migration login role; both passwords are persisted only in the encrypted host store before PostgreSQL is changed. Migration credentials and metadata are never included in runtime secret lists, the app environment, prompts, workspace files, logs, Git, build inputs, or public APIs. Better Auth also receives a stable generated `BETTER_AUTH_SECRET` when missing. Existing custom database URLs are preserved and never trigger DCK database provisioning or automatic migration. Database names use `dck_<slug>` where possible and a deterministic bounded form for slugs that exceed PostgreSQL's 63-byte identifier limit. Creation is idempotent and never adopts or replaces an existing database whose owner does not match the encrypted project identity; failures block the lifecycle operation without exposing credential values. Deletion removes only the exact project database and its two managed roles after ownership and role-scope checks.

The service changes ACLs only inside the app database. It does not revoke cluster-wide `PUBLIC CONNECT` on other databases because that shared change could break existing apps; where strict cross-database connection isolation is required, an operator must plan and audit a separate cluster ACL policy. PostgreSQL's default `PUBLIC CONNECT` may remain available elsewhere in the shared cluster. On explicit deploy-like lifecycle actions, standard PostgreSQL Prisma migration files run in a short-lived, read-only, non-root psql container attached only to the `dck` network. Each migration is checksum-tracked and applied in its own transaction using the migration role; the runner receives its password through a mode-0600 temporary env file outside the workspace, removed after execution. The runtime role has no DDL, ownership, `TRUNCATE`, or project-defined function execute grants; only the scoped DML and sequence grants required by the app are synchronized after migrations. The runner accepts schema DDL only, rejects psql commands, transaction controls, privilege/ownership changes, procedural SQL, external/cross-database features, arbitrary function calls, and edits to the protected migration ledger. Unsupported or malformed migrations fail closed before the app lifecycle continues. Existing generated databases without encrypted migration metadata and custom URLs are not auto-adopted or migrated; manual operator review is required rather than weakening ownership checks.

During an explicit deploy/rebuild/start/restart/publish/unpublish operation, the service validates required values, preserves safe non-secret entries from the existing project `.env` and declared local Compose `env_file` inputs, adds missing non-secret `.env.example` defaults and `APP_BASE_PATH`, and removes recognized or configured secret keys. If an environment file cannot be safely parsed, startup moves the entire original file to `/var/lib/dck-webgen-control/legacy-env-quarantine/` with root-only directory permissions and a mode-0600 root-owned archive; the workspace copy is removed, the bytes are preserved for operator review, and the project remains blocked from lifecycle operations until an administrator resolves the archive and clears the review block by removing that archive. No ambiguous content is parsed into a replacement environment file or used to start an app. If secure quarantine fails, the service removes the workspace copy and refuses to start; deployment health checks then prevent Canvas from starting through the deployment flow. Diagnostics contain no file contents. A mode-0600 environment file is created under the systemd-managed volatile `/run/dck-webgen-control` directory, outside the workspace and persistent store. A temporary Compose overlay attaches that file only as the `app` service's runtime `env_file`; it is removed after Compose creates/updates the container and `/run` is cleared on service stop. The runtime file is not provided to the image build, and Compose validation uses `--no-env-resolution`. Compose declarations that place a runtime secret in `environment` or `build.args` are rejected. Declared project-local Compose environment files are scrubbed of recognized legacy secrets at control-service startup and before lifecycle operations; safe user configuration is retained and existing containers are not restarted by startup cleanup.

Manage custom variables from each Web Generator project row via **Environment**. The dialog supports manual Sensitive/Non-sensitive classification per key and keeps both classes encrypted. Saving, classifying, or deleting a value does not deploy or restart the application. Changes apply the next time the user explicitly runs Deploy preview, Rebuild, Start, Restart, Publish, or Unpublish. Blank edits retain the saved value; deletion is a separate action. Values are not prefetched or shown by default: an authenticated user receives one value only after choosing **Show value**, and can hide it again. No reveal value is logged or sent to analytics. Runtime status includes a host-derived `has_deployment` flag from the validated saved preview route or publication, independent of whether the app is currently running. The project menu shows **Deploy preview** only before a successful preview or publication, **Rebuild** for existing deployments, **Start** for stopped deployments, and does not offer Publish again when a project is already published.

## Legacy migration

Legacy `<ENV_NAME>_<PROJECT_SLUG>` Agent Secret Manager entries are listed by name only. The service offers only exact slug-suffix candidates; unsuffixed entries are never imported automatically. A user must explicitly choose **Prepare move**. Ambiguous suffixes require a second explicit confirmation. The service copies the value into an encrypted, inactive pending record; it never deletes the source because the Agent Secret Manager does not offer a compare-and-swap delete. The user removes the source in Settings → Secrets, then chooses **Verify source removal**. The service activates the encrypted copy only after a fresh authenticated read confirms the source is absent (404), and the migrated key defaults to Sensitive. If the source still exists or the read is uncertain, the pending value stays encrypted and inactive; if the source changed, the pending copy is refreshed before verification. Migration values are never displayed or logged; the Environment dialog's separate explicit reveal action applies only after activation.

## Owner seed, Compose, and lifecycle

The app-local owner endpoint accepts the signed JSON object described by the WebGen skill and returns 2xx, or 409 for an already-created owner. The service signs the exact ordered UTF-8 JSON array `[version, project_slug, conversation_id, issued_at, expires_at, nonce, email, username, password]`, preserving password Unicode and whitespace. Seeds are AES-GCM encrypted in process memory, expire within 15 minutes, and are retained until delivery succeeds (including an idempotent 409); authorization lasts at most five minutes. No seed is written to metadata, runtime files, logs, or prompts.

The verification key is derived deterministically per slug from the persistent master key using HKDF-SHA256. Owner health and delivery use the deterministic `<slug>-app` container's private IP on external Docker network `dck`, port 3000, and the active basePath. Source YAML and rendered Compose JSON are validated against the single-app policy before Docker commands run; host mounts, named volumes, and privileged configuration are rejected. Builds are serialized; status polling is limited to Compose-managed projects. The service returns the Agent Server-visible workspace path (`/projects/webgen/<slug>`), not the host filesystem path.

Unpublished apps use `APP_BASE_PATH=/preview/<slug>` and `preview-<slug>.conf` inside the Canvas server. Publish explicitly rebuilds with an empty basePath and replaces the preview route with `published-<slug>.conf` at nginx HTTP scope, using the wildcard certificate paths in [DEPLOYMENT.md](DEPLOYMENT.md). Unpublish rebuilds for preview and removes the published route. There is one active mode, without a second container or preview domain. Readiness polls for up to `WEBGEN_READINESS_TIMEOUT` seconds (default 120, maximum 300); Canvas proxy/client lifecycle timeouts are 45 minutes. Failed publication attempts restore saved routes and metadata and rebuild the previous mode when needed; failed recovery is reported explicitly.

**Delete is destructive:** projects requiring a database preflight PostgreSQL before removing routes or containers. Cleanup removes routes, runs the fixed Compose-down operation, and removes project files before dropping only that project's deterministic database and generated runtime role through maintenance database `postgres`; only after those steps does it remove that project's encrypted runtime secrets. It never uses `DROP OWNED` or a cross-project cleanup. A filesystem failure does not drop the database, and rollback redeploys with the retained secret record. If later database or secret-store cleanup is uncertain after workspace removal, the API reports recovery is required and retains encrypted runtime state for an administrator. Explicitly database-free projects skip PostgreSQL. Confirmation is a UI responsibility. The trusted internal deployment now also grants Canvas root-equivalent host Docker socket access; these controller policies do not constrain direct agent Docker commands. See [deployment access and verification](DEPLOYMENT.md#trusted-internal-docker-access).
