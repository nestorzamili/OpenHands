# WebGen app runtime secrets (WR-020)

## Intent

Provide project-scoped app runtime credentials without reusing the agent's Secret Manager. Agent `LookupSecret` and app runtime configuration remain different scopes.

## Requirements

1. Each project receives a stable canonical UUID in `.dck.json`; malformed or duplicated identities fail closed, and corrupt/unreadable metadata is never rewritten by an ID migration. The host-only encrypted store is indexed by this UUID, and every request also resolves and validates its project slug/path.
2. Runtime values and per-key Sensitive/Non-sensitive classifications are AES-GCM encrypted at rest using a dedicated HKDF-derived key and root-only host state. The master key is not in Canvas's bind-mounted `config/` directory. List/status responses may return project ID, variable names, configured state, classification, and migration state, but never values. A separate value endpoint returns one value only after the request passes the existing authenticated session check; it sends `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Legacy values default to Sensitive. Both classifications remain encrypted and app-only; classification is descriptive and does not grant agents access.
3. Values must not enter agent-readable workspace files, prompts, transcripts, logs, analytics, Git, image builds, or status/list responses. The project `.env` may hold safe non-secret user configuration, missing non-secret `.env.example` defaults, and `APP_BASE_PATH`; recognized legacy secret entries are scrubbed. If ambiguous syntax prevents safe parsing, the whole original `.env` is moved outside the workspace into root-private host quarantine, with contents retained for administrator review. No workspace copy is left or used to start an app; a durable review archive blocks lifecycle operations until an administrator restores only safe values and removes the archive. If quarantine cannot be secured, startup fails closed and removes the workspace copy where possible; it must never continue starting an agent with that file exposed.
4. An explicit lifecycle operation creates a short-lived, mode-0600 host env file in a root-only volatile runtime directory outside the workspace and persistent store, and attaches it only to the Compose `app` service. Runtime secrets are not interpolated into Compose YAML or build args; conflicts in `environment` or `build.args` are rejected. Temporary plaintext is removed after Compose returns and the volatile directory is cleared at service stop.
5. Saving, editing, classifying, and deleting variables never deploys or restarts an app. UI communicates that values apply on the next Deploy preview/Rebuild/Start/Restart/Publish/Unpublish. Blank edits preserve the current value while allowing classification changes; delete is explicit. Values are never prefilled or automatically revealed. An authenticated user may explicitly reveal a value in the Environment dialog, which hides it again on request and clears it after edits, deletion, refresh, or dialog close.
6. Legacy migration lists name-only candidates that match an exact project slug suffix. Unsuffixed entries are not candidates. Ambiguous suffixes require explicit confirmation. The service encrypts a pending record first and never deletes the Agent Secret Manager source because no compare-and-swap delete is available. The user removes the source explicitly, then the service activates the pending value only after a fresh authenticated read confirms the source is absent. Existing or unreadable sources leave the value encrypted and inactive; changed source values refresh the pending copy before verification.
7. The UI is accessible and responsive, with loading/empty/error/saved states and retained form inputs on errors. The concise dialog uses a scrollable list for many variables, offers a manual classification per key, defaults new and migrated keys to Sensitive, and reveals a value only after a user action. Runtime variables are identified as app-only and separate from the Agent Secret Manager.
8. Project deletion retains encrypted runtime secrets throughout any rollback; recovery redeploys use the same runtime-secret file path and values. Store mutation failures restore the in-memory snapshot.
9. Backup/restore always preserves `/var/lib/dck-webgen-control` (ciphertext and master key) as a pair with root-only ownership and permissions; never restore the master key into Canvas `config/`.
10. On an explicit deploy-like lifecycle action, projects with `needsDatabase: true` or Better Auth receive a stable generated `DATABASE_URL` when no value is configured. The host stores it encrypted before provisioning an idempotent per-project PostgreSQL database, a non-owner runtime role, and a distinct database-owner migration role. Both role credentials and the migration URL remain only in the encrypted host store; they never enter project Environment APIs, app env files, prompts, workspace, logs, Git, build inputs, or public responses. The runtime role is `LOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, has no memberships, and receives only CONNECT/USAGE plus narrowly scoped DML/sequence grants; it cannot create schema objects or access migration metadata. ACL changes are limited to that app database; cluster-wide `PUBLIC CONNECT` on other databases is not altered, so effective cross-database connection isolation requires a separately audited cluster ACL policy. Better Auth receives a stable generated `BETTER_AUTH_SECRET` when missing. User-provided database URLs are preserved and never auto-provisioned or migrated. SQL identifiers and literals are safely quoted; failures block lifecycle operations without leaking values; provisioning never adopts or drops existing data. Deletion drops only the exact service-managed project database and its two roles after encrypted identity, ownership, and role-scope checks.
11. Lifecycle actions reflect host-reported state: a `has_deployment` status flag is derived from validated saved preview/publication metadata, not from running state alone. Show Deploy preview only before a successful preview/publication; hide it for running, stopped, and published deployments; show Rebuild for existing deployments and Start for stopped deployments. A published project does not offer duplicate Publish; Unpublish remains available. Unknown/starting state must not be treated as a first deployment.
12. Explicit deploy-like actions may apply standard PostgreSQL Prisma migrations only through a short-lived, non-root, read-only psql container on network `dck`, using the separate per-project migration role via a mode-0600 host env file outside the workspace. Migrations are checksum-tracked and individually transactional. The runner accepts schema DDL only and rejects psql commands, transaction controls, grants/ownership changes, procedural SQL, arbitrary function calls, and edits to the protected ledger; unsupported migrations fail closed. It never passes migration credentials to the app runtime role or exposes them to the agent. Existing databases without matching encrypted management metadata are not adopted or migrated. No cluster-wide ACL changes are performed by per-project lifecycle actions.

## Verification

- Python service tests: encrypted-at-rest values and classifications, project isolation, Sensitive defaults for legacy and generated credentials, blank edits that change classification without replacing the value, explicit reveal only after real session authentication, project scoping, no-store/nosniff headers, no values in list/status responses, stable auto-generated Better Auth/database credentials, separate runtime/migration role provisioning and least-privilege grants, safe SQL quoting, API-key validation and project ID/slug binding; corrupt metadata is unchanged; no plaintext workspace `.env`; safe non-secret values survive scrubbing, while exact `TOKEN` and secret-like keys are removed even when not in the store; ambiguous `.env` contents are privately quarantined with original bytes and restrictive owner/mode, no readable workspace copy remains, quarantine fallback works, quarantine failure removes the workspace copy and blocks startup without leaking contents, and lifecycle materialization stays blocked while the review archive exists; identical secure `.env` files are not rewritten; only the app service receives a protected temporary env-file; missing required value and Compose secret/build conflicts fail before deploy; explicit two-step migration, ambiguity confirmation, source-changed/source-still-present/absent cases, delete rollback with secrets re-injected, filesystem failure does not drop the database, and write-failure memory consistency. Migration tests validate Prisma discovery/checksums, strict SQL allowlisting, runner secret isolation, ledger protection, transactional application, failure redaction, and scoped cleanup. A tar backup/restore round-trip proves the master key and encrypted store remain a matched, decryptable pair with private permissions.
- Docker integration test (opt in with `WEBGEN_DOCKER_INTEGRATION=1`): saves a value through the runtime-secrets PUT route, runs the actual lifecycle action and Docker Compose, then uses `docker exec` to compare the value inside the running app container; also verifies the host temporary env file and workspace `.env` do not retain it. This is the check that proves the value is actually container-visible; the regular mocked tests alone do not.
- Proxy tests: only GET routes forward with the session API key; all mutating paths, including legacy-secret DELETE, remain blocked.
- UI tests: the three-dot menu opens the project Environment manager, including before a runtime exists; stored values stay hidden until explicitly revealed and can be hidden again; add/edit can select classification; blank edit retains the value while saving classification; delete uses runtime-secret endpoints only; migration requires explicit confirmation and reports the removal state; save does not call lifecycle actions; Deploy preview/Rebuild/Start/Publish visibility follows preview, stopped, running, and published state.
